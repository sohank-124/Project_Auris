# Clock Domain Analysis

> **Project Auris** — Clock domain inventory and crossing analysis
> **Last updated:** 2026-07
> **Status:** Authoritative. The four-domain model below is reflected
> in `fpga/rtl/auris_pkg.sv` (`clock_domain_t` enum) and in
> `fpga/constraints/cmod_s7_25.xdc` (the three `create_clock` and
> one `create_generated_clock` lines plus the four `set_false_path`
> constraints).

This document explains *why* the FPGA RTL has three reset networks
instead of one, *why* the four clock domains never meet without
synchronizers, and *what* timing constraints are applied at the
boundary. The intent is to make the CDC strategy reviewable by anyone
new to the codebase.

---

## 1. Clock Tree

The design has four logical clock domains, three of which physically
exist in the FPGA. The fourth (the ESP32's I2S master) is generated
entirely by the ESP32 and is observed by the FPGA only at the I2S RX
and I2S TX ports.

| Domain ID | Source                          | Frequency            | Generated By         | Drives                                                                                  |
|-----------|---------------------------------|----------------------|----------------------|-----------------------------------------------------------------------------------------|
| `CD_AUX`  | Onboard 12 MHz oscillator       | 12.000 MHz           | Cmod S7-25 crystal   | MMCM `clk_in1` input only. Nothing else is in this domain.                              |
| `CD_DSP`  | MMCM `clk_out1`                 | 96.000 MHz           | MMCME2_BASE          | All DSP pipeline stages: input_buffer, window_apply, fft_256, spectral_proc, ifft_256, overlap_add, output_buffer, reg_file, mode_ctrl, status_mon, MMCM-side of all CDC FIFOs, mode-change detection. |
| `CD_I2S`  | ESP32 I2S peripheral            | BCLK 3.072 MHz / LRCLK 48 kHz | ESP32 I2S master   | `i2s_rx.sv`, `i2s_tx.sv`, BCLK-side of the I2S↔DSP CDC FIFOs, LRCLK 2-FF synchronizer. |
| `CD_SPI`  | ESP32 SPI peripheral            | ~10 MHz              | ESP32 SPI master     | `spi_slave.sv`, SPI-side of the SPI↔DSP CDC handshake, read-data return path.            |

**Notes**

- The `CD_AUX` domain exists only to feed the MMCM. After the MMCM
  locks, every flip-flop downstream of the MMCM is in `CD_DSP` and
  the `CD_AUX` net can be ignored for timing.
- `CD_I2S` is technically a BCLK domain with a 48 kHz LRCLK
  embedded inside it. The two are *not* separate domains from a
  CDC perspective — the LRCLK is registered into the BCLK domain by
  the I2S RX/TX blocks themselves and the 2-FF synchronizer in
  `top.sv`.
- `CD_SPI` is asynchronous to `CD_DSP` and asynchronous to `CD_I2S`.
  The ESP32's I2S and SPI peripherals are clocked from the same
  APB-derived root, but that fact is invisible to the FPGA; the
  FPGA sees two independent asynchronous clock inputs.

## 2. Clock Domain Crossings (CDC)

The design has three logical CDC boundaries, instantiated as three
module pairs. The table below summarises the *direction*, the
*signal(s) crossing*, the *method*, and the *justification* for
each crossing.

| #  | Source Domain | Dest Domain | Signal(s)                                               | CDC Method                                        | Justification                                                                                                          |
|----|---------------|-------------|---------------------------------------------------------|---------------------------------------------------|------------------------------------------------------------------------------------------------------------------------|
| 1  | `CD_I2S`      | `CD_DSP`    | 24-bit L/R audio samples, sample-valid strobe           | Async FIFO with Gray-coded read/write pointers, 4-deep | Audio is a continuous stream at 48 kHz. The I2S and DSP clocks are unrelated, so a FIFO is the only correct mechanism. A 4-deep FIFO absorbs the worst-case jitter from the DSP-side burst consumer. |
| 2  | `CD_DSP`      | `CD_I2S`    | 24-bit L/R processed audio samples                      | Async FIFO with Gray-coded pointers, 4-deep      | The DSP pipeline produces samples in bursts (one per frame boundary); the I2S TX consumes them at exactly 48 kHz. A FIFO smooths the rate mismatch. |
| 3  | `CD_SPI`      | `CD_DSP`    | 7-bit address, 24-bit data, write-enable, read-enable   | 2-FF synchroniser on data + dedicated req/ack handshake | Register writes are infrequent (≤ 1000 per second in steady state) and unidirectional. A 2-FF synchroniser is sufficient and uses fewer BRAMs than a FIFO. The req/ack handshake guarantees the 24-bit payload is held stable until the destination acknowledges. |
| 4  | `CD_DSP`      | `CD_SPI`    | 24-bit read data, read-data-valid strobe                | 2-FF synchroniser on data + 2-FF on valid          | Read data is a single 24-bit word per read transaction. A 2-FF synchroniser is sufficient. The valid strobe uses an independent 2-FF chain. |

**Notes**

- The FIFOs in crossings 1 and 2 are dual-clock with Gray-coded
  pointers and 4 entries deep. Gray coding guarantees that exactly
  one pointer bit changes per increment, so the destination always
  reads a consistent pointer value.
- The req/ack handshake in crossing 3 uses **two independent 2-FF
  chains**: one for the request pulse and one for the data payload.
  The source holds `we_o` and `wdata_o` stable until the destination
  acknowledges; the destination generates the ack only after the
  payload is safely latched.
- The 24-bit read data in crossing 4 is registered into the SPI
  domain by a 2-FF chain. Because the data originates from a
  register file, the read latency is a fixed 1 DSP cycle plus 2 SPI
  cycles of synchroniser delay; the protocol handles this latency
  transparently.

## 3. Metastability Mitigation

Every asynchronous crossing is a potential metastability hazard. The
following techniques are applied to bound the failure probability.

### 3.1 2-FF Synchronisers

The 2-FF synchroniser is the workhorse of the design. It is used
wherever a single-bit (or narrow multi-bit) signal crosses between
two asynchronous clocks. The two-stage register chain gives the first
flip-flop up to one destination-clock period to resolve from a
metastable state before the second flip-flop samples it.

Both the `.synchronizer` and the `*.rst_synchronizer*` instances in
the RTL are tagged with `ASYNC_REG = "TRUE"` so Vivado's placer
keeps the two flip-flops physically adjacent. This minimises the
clock-to-out skew between the stages and reduces the probability
of a metastable value being sampled by the second stage.

### 3.2 Async FIFOs with Gray-Coded Pointers

For the 24-bit audio sample streams, a single 2-FF synchroniser is
inadequate: a 24-bit value is not a single bit, so the destination
cannot tell which bits belong to the same word. Instead, the design
uses an asynchronous FIFO with Gray-coded read and write pointers.

Gray coding has the property that exactly **one bit** changes per
increment, so the destination can sample the pointer at any time and
always read a value that is either the *old* pointer or the *new*
pointer — never a mix. The empty/full condition is then derived
from comparing the two pointers; the result is correct in both
cases, and the worst-case latency is one destination-clock cycle
for the empty/full flag to update.

### 3.3 Req/Ack Handshake for Register Writes

Register writes are rare (a handful per second at most) and the
data is held stable for hundreds of DSP cycles. The req/ack
handshake guarantees the destination has captured the payload
before the source releases it. This is implemented as a 1-bit
request pulse synchronised by 2 FFs, and a 1-bit acknowledge pulse
synchronised by 2 FFs in the opposite direction. Four flip-flops
total, zero possibility of data loss.

### 3.4 MTBF Estimate

The mean time between failures (MTBF) of a single 2-FF synchroniser
on Spartan-7 at room temperature is on the order of **10⁹ hours** per
synchroniser at the design's data-toggle rate. The design has
approximately 10 synchronisers (4 in CDC crossing 3, 2 in crossing 4,
plus the LRCLK and reset synchronisers). Even with conservative
assumptions, the aggregate MTBF exceeds the projected operational
lifetime of the device by several orders of magnitude.

### 3.5 Reset Synchronisation

The MMCM `locked` output is asynchronous to every downstream clock
domain by construction. The `reset_sync_stretch` helper module
implements a 2-FF synchroniser plus a 16-bit shift register
"stretcher" that holds the destination reset asserted for
`STRETCH_CYCLES + 2` cycles after the source reset de-asserts. The
stretch is implemented as an SRL16E on Spartan-7, which costs zero
flip-flops and zero LUTs.

There is one `reset_sync_stretch` instance per clock domain (DSP,
I2S, SPI), each driven from the MMCM `locked` signal and clocked by
its respective destination clock.

## 4. Timing Constraints Summary

The timing constraints are in
[`fpga/constraints/cmod_s7_25.xdc`](../../fpga/constraints/cmod_s7_25.xdc).
The most relevant lines for CDC are:

| Constraint                                                              | Purpose                                                                              |
|-------------------------------------------------------------------------|--------------------------------------------------------------------------------------|
| `create_clock -name clk_12mhz -period 83.333 [get_ports clk_12mhz]`     | Primary clock: 12 MHz onboard oscillator. Period in nanoseconds.                    |
| `create_clock -name spi_sclk_i -period 100.0 [get_ports spi_sclk_i]`   | SPI clock: ~10 MHz from ESP32.                                                       |
| `create_clock -name i2s_bclk_i -period 325.521 [get_ports i2s_bclk_i]` | I2S BCLK: 3.072 MHz = 64 × 48 kHz.                                                   |
| `create_generated_clock -name clk_dsp -multiply_by 50 -divide_by 6.25 ...` | Generated 96 MHz DSP clock (12 × 50 / 6.25 = 96 MHz; VCO = 600 MHz).            |
| `set_input_delay -clock spi_sclk_i ±5.0 ...`                            | SPI input delay bounds (covers ESP32 output skew and PCB flight time at 10 MHz).    |
| `set_input_delay -clock i2s_bclk_i ±10.0 ...`                           | I2S input delay bounds (covers PCB skew and INMP441 output delay at 3.072 MHz).     |
| `set_false_path -from [get_clocks spi_sclk_i] -to [get_clocks clk_dsp]`| Disable timing analysis across the SPI→DSP CDC. The CDC is safe by construction.    |
| `set_false_path -from [get_clocks clk_dsp] -to [get_clocks spi_sclk_i]`| Same, in the reverse direction.                                                      |
| `set_false_path -from [get_clocks i2s_bclk_i] -to [get_clocks clk_dsp]`| Disable timing analysis across the I2S→DSP CDC.                                      |
| `set_false_path -from [get_clocks clk_dsp] -to [get_clocks i2s_bclk_i]`| Same, in the reverse direction.                                                      |
| `set_false_path -to [get_ports {status_led_o status_clip_o ...}]`       | Async output paths: the LEDs and the RGB LED are too slow to need timing closure.    |
| `(* ASYNC_REG = "TRUE" *)` (RTL attribute)                             | Tags every synchroniser flip-flop pair so Vivado placer keeps them physically close.|

### 4.1 Why `set_false_path` and not `set_max_delay -datapath_only`?

The `set_false_path` constraint tells Vivado's timing engine *not*
to attempt to close timing across the CDC boundary. This is correct
because the CDC is safe-by-construction: the FIFOs and synchronisers
absorb meta-stability by design, and the destination uses the
synchronised signal only after it is stable. Trying to close timing
across these paths would force Vivado to add unnecessary pipeline
stages, increasing latency and degrading the audio pipeline's
worst-case slack.

A commented-out alternative using `set_max_delay 100.0` is included
in the XDC for development debugging. If a future revision needs
bounded CDC latency (e.g., for hard real-time scheduling), uncomment
those four lines.

### 4.2 Async Reset Path

The `MMCM locked` signal is asynchronous to every downstream clock
by construction. The reset synchroniser's D-pin is the metastability
absorber, and is false-pathed explicitly:

```tcl
set_false_path -from [get_ports clk_12mhz] \
    -to [get_pins -hierarchical -filter {NAME =~ *rst_synchronizer*/D}]
```

The `NAME =~` filter is permissive: if a synchroniser instance is
renamed in a future revision, the filter still matches by the
sub-string `rst_synchronizer`. If the RTL is refactored away from
that naming, update the filter.
